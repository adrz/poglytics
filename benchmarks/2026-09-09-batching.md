# ClickHouse ingestion benchmark — 9 September 2026

Per-table batching reduced average ClickHouse CPU during ingestion by **29.7%**,
inserts/new parts by **92.2%**, and completed merges by **95.5%** in this local test.
All four runs stored the same 39,600 distinct records with matching content checksums
and zero write errors. These are measurements of synthetic database ingestion,
not predictions for total machine CPU or live Twitch throughput.

Including the fixed merge tail, total container CPU time fell **26.8%**. Server
background tasks still consume CPU even when ingestion generates fewer parts.
The paced workload finishes in approximately one minute in both modes; this test
does not establish a maximum-throughput speedup.

| `raids` | 44 | 29 | 2 |
| `bits` | 35 | 28 | 2 |

The tradeoff is delayed visibility. The largest observed oldest-row ages at flush
completion were **5.24 seconds** for text/other, **10.17 seconds** for snapshots,
and **30.32 seconds** for rare events. These include write time after the timer
expires; they exclude time spent upstream of the writer. The new writer retained
at most 3,771 rows in this workload, under its 32 MiB estimated payload limit.
Buffered data remains vulnerable to process crashes; graceful shutdown drains it.

## Method

- Host: macOS arm64; Go 1.27.1. Docker Linux VM: 11 CPUs, 8,214,716,416 bytes RAM,
  Docker 29.7.2. Each fresh benchmark container was limited to 2 GiB RAM, with no
  additional CPU quota. Container data used anonymous Docker volumes.
- ClickHouse 26.8.2.7; identical local image digest for every run:
  `sha256:b4ece5865bac92bd73bffa8cb92aa220a45515159bfb36488de55dca8f40a693`.
- 600 synthetic chat events/second plus 60 snapshots/second for 60 seconds.
  Snapshots arrived in pages of 100. Deterministic seed 42; 65% text, 33.8% other,
  0.4% subscriptions, 0.3% notices, 0.15% bans, 0.1% each deletions/raids/bits,
  and 0.05% hosts. This approximates the previously observed event mix and also
  exercises the bits and hosts tables. Payloads are synthetic, not sampled messages.
- The existing ClickHouse schemas, Go driver and insert methods were used in both
  modes. Original policy: 500 mixed chat rows or a one-second tick, immediate
  snapshot pages. New policy: 5,000 rows / 5 seconds for text/other, 1,000 / 30 seconds
  for rare events, 1,000 / 10 seconds for snapshots.
- Both policies run through the production `db.IngestWriter`. The legacy policy
  reproduces the previous batching thresholds; this is not a comparison between
  two historical scraper binaries. Fixture generation, IRC parsing and application
  message conversion are outside the measured replay.
- Each run used its own fresh container and database. Schema creation plus three
  seconds of settling preceded measurement. The final flush and a fixed 10-second
  merge tail were included; no active merges remained at the final sample. This
  does not rule out future background merges. Containers and their anonymous
  volumes were removed afterward. No scraper credentials or existing data were used.
- Container CPU comes from cumulative cgroup-v2 `usage_usec` deltas. Ingestion CPU
  percentage is CPU time divided by feed-and-drain wall time, with 100% representing
  one core. Small Docker-exec sampling costs and server background work are included.
  It is not a percentage of all 11 CPUs. Go CPU comes from process `getrusage`.
- Inserts and INSERT CPU are scoped to the test database in
  [ClickHouse `system.query_log`](https://clickhouse.com/docs/reference/system-tables/query_log).
  New parts, completed merges and merge CPU come from
  [`system.part_log`](https://clickhouse.com/docs/reference/system-tables/part_log).
  Log flushing and verification happen after CPU measurements.
- Verification checks each table's count, unique synthetic record key, inserted
  row count, and an order-independent checksum of all stored columns except `id`.
  The existing ID generator depends on position within a batch, so these IDs change
  with batching. In the raw JSON, legacy per-table chat ages of zero mean they were
  not collected: legacy chat flushes are labelled `mixed`.

Two runs per mode give an initial local estimate, not statistical confidence across
hosts and workloads. Existing large tables, different event rates, burstiness,
payload sizes, dashboard queries, and host load can change the CPU savings.
The replay catches up after delayed submissions rather than dropping events;
submission lag measures producer delay, not the live scraper's queue size.

## Reproduce

```sh
make benchmark BENCH_ARGS='--seconds 60 --rounds 2 --output benchmarks/repeat.json'
```

Use `--image` with the digest above to select the same installed image. The harness
does not pull images automatically. Source: [Python harness](../scripts/benchmark.py),
[Go replay](../cmd/ingest-benchmark/main.go), [production writer](../internal/db/batching.go).
Raw measurements: [2026-09-09-batching.json](2026-09-09-batching.json).

Validation: `make check` passed, including the full Go race test suite and `go vet`.
