Review completed on 8 September 2026. The highest-impact problems were message corruption, incomplete shutdown, and competing connection lifecycles. I reviewed the application, parser, Twitch client, database backends, configuration, CI, and deployment documentation, then implemented the fixes below. Existing local connection changes were incorporated; the pre-existing untracked tests, binary, and Compose file were retained.

**Implemented findings**, ordered by impact:

1. **High — shutdown discarded queued messages and repeatedly closed the shared database.** The database writer previously stopped on context cancellation after flushing only its local batch, leaving up to 100,000 queued messages unread. Individual IRC connections also closed the same database. [Pool shutdown](internal/app/pool.go) now stops and waits for producers, closes the queue, drains it, and closes the database once. Startup and background discovery are included in the wait. Concurrent shutdown calls are safe. A regression test verifies that all 1,201 queued messages and their tags survive shutdown, with exactly one database close.

2. **High — reconnects could leave old workers using a replacement socket.** JOIN tasks outlived their socket, dial retries ignored cancellation, and the reader retried terminal errors on the same connection. [Connection ownership](internal/app/pool.go) now waits for both reader and JOIN worker before reconnecting. Dial attempts have a timeout and cancellation; the pool applies bounded exponential backoff to connection and read failures. [Socket shutdown](internal/app/ircconnection.go) closes the socket immediately to unblock I/O. Channel assignments survive reconnection, including channels discovered after startup.

3. **High — tagged events stored protocol metadata as message text.** Searching for the first ` :` matched the boundary before the server prefix in tagged messages. This corrupted bans, deletions, subscriptions, notices, and hosts. Searching for a channel name could also match the same text inside an earlier tag. [Parsing](internal/app/parser.go) now finds the trailing parameter after skipping tags and the prefix, strips wire terminators while preserving message spaces, decodes tag escapes once, classifies full chat clears separately, and uses valid server timestamps. Regression tests reproduced all these failures before the fix.

4. **High — partial reads could silently corrupt the next IRC message.** A timeout discarded bytes already returned by the reader, so a fragmented message could be parsed from its suffix. [The reader](internal/app/socket_reader.go) now preserves partial lines across timeouts and bounds a line at 64 KiB. Oversized input and terminal I/O failures force a reconnect. Failed PONG writes also end the session. Tests cover fragmentation, oversize input, idle-reader cancellation, and JOIN cancellation during pacing.

5. **High — OAuth expiry permanently broke subsequent channel discovery.** [The Twitch client](internal/twitch/client.go) now renews expired tokens and retries once after a 401, sharing renewal between concurrent requests. OAuth credentials and pagination cursors are properly encoded. Discovery HTTP requests inherit the pool's cancellation context. Tests verify special characters, token replacement, and concurrent renewal.

6. **Medium — rediscovery lost ownership and exceeded channel capacity.** Discovery used currently joined channels as its ownership registry, so disconnected or pending channels could be assigned again elsewhere. New assignments were not retained for reconnects, and limits were not enforced. [Assignment handling](internal/app/channels.go) now separates desired channels from socket state. Rediscovery deduplicates assignments and respects both total and per-connection limits. A new socket has one JOIN worker; updates signal that worker instead of starting overlapping sweeps. JOIN commands are paced at ten channels every five seconds, including successive updates. This lowers the configured per-connection attempt rate and increases startup/rejoin time.

7. **Medium — configuration could crash or ignore deployment overrides.** A lone quote in `.env` caused a slice panic; process variables were ignored whenever the file existed. [Configuration loading](internal/config/config.go) now returns errors for malformed quotes, applies process overrides including empty values, and defaults ClickHouse to its native port. [The entry point](cmd/poglytics-scraper/main.go) also reads these settings, rejects invalid channel counts and ports before dividing or starting services, and avoids overflow in the connection-count calculation. Failed pool initialization releases its database handle.

8. **Medium — simultaneous SQLite writers and misleading overflow metrics.** Chat and stream snapshots share the same SQLite database. Its pool now serializes access through one connection, including in-memory databases. The database regression test exercises concurrent chat and snapshot writes. Queue overflow now increments the existing dropped-message counter. CI runs the test suite with the race detector. New tests exercise production code; the older local `channels_test.go` still tests a separate copied implementation and should eventually be replaced.

**Remaining findings and recommended follow-up**, also ordered by impact:

1. **High — database outages can still lose records.** Every backend's `SaveChatMessageBatch` commits event groups separately. If a later group fails, earlier groups remain committed and subsequent groups are skipped. The central writer reports the error and discards that batch. Retrying blindly would duplicate committed rows. Define delivery guarantees, persist stable event IDs, and introduce atomic relational batches or an explicit replay/idempotency strategy. A durable queue is needed for recovery after process crashes. This review fixes normal shutdown draining; it does not make ingestion durable during database failures. Database calls also lack operation contexts, so an unresponsive database can still delay shutdown.

2. **High — ClickHouse loses fields and its generated IDs are not unique.** [Its text-message table and insert](internal/db/clickhouse.go) omit `bits_amount`, `color`, and `raw_message`, although PostgreSQL and SQLite preserve them. Cheers remain `text_message` events, so their amounts disappear in ClickHouse. `generateID(timestamp, index)` can collide across batches; server timestamps have millisecond precision, making batch-local indices especially unsuitable as identities. Plan a schema migration that retains these fields and Twitch message IDs. Raw tags now reach the database interface, but none of the backends persists the full tag map.

3. **Medium — a successful JOIN write is still treated as membership confirmation.** A server may reject or silently ignore a join. The current counters describe successfully sent commands, and disconnected sockets can retain stale joined counts until reconnect. Track pending versus acknowledged membership using server replies, and handle rejected joins explicitly. Similarly, `IsConnected` means the handshake was sent, rather than server authentication being acknowledged. Twitch documents these distinct responses in its [IRC connection and JOIN reference](https://dev.twitch.tv/docs/chat/irc/).

4. **Medium — offline-channel retention needs an explicit policy.** Existing assignments remain reserved when a channel goes offline. Once the configured capacity is reached, newly discovered channels are skipped with a warning. To continuously cover the most active channels, add an inactivity grace period and PART/reassignment policy. Increasing the configured limit alone does not solve this over long runtimes.

5. **Medium — API rate-limit handling remains incomplete.** The client records rate-limit headers only on successful responses and does not wait for reset after a 429. Large discovery runs can still abort mid-scan. Add cancellation-aware reset handling with a bounded retry policy.

6. **Medium — connection strings and deployment defaults need attention.** PostgreSQL and ClickHouse interpolate credentials directly into connection strings, so reserved characters can break authentication. Use driver options or encoded URL components. The root Compose file exposes ClickHouse's native port as 19000, whereas the example client configuration uses 9000; it also does not create the configured `twitch_chat` database. The README references a missing build script and analytics binaries. The working build command is `go build -o build/poglytics-scraper ./cmd/poglytics-scraper`.

The documented Twitch account limits are 20 JOIN attempts per ten seconds and 100 concurrent channels, with specified exceptions. These do not establish a supported capacity for this project's anonymous `justinfan` connections. The existing 1,500–2,000-channel capacity claims remain unverified; the slower pacing is a conservative application setting, not a guarantee of acceptance. See [Twitch chat limits](https://dev.twitch.tv/docs/chat/#join-rate-limits). Tag decoding was checked against the [IRCv3 message-tag specification](https://ircv3.net/specs/extensions/message-tags.html#escaping-values).

Validation uses the installed Go 1.27.1 toolchain: the race-enabled suite, `go vet ./...`, and an executable build. Tests use local fake IRC sockets, an HTTP transport fake, and SQLite; live Twitch, ClickHouse, PostgreSQL, Docker deployment, sustained production throughput, and the declared Go 1.24 toolchain were not exercised. The existing suite passed before the new regression tests were added, illustrating why its earlier green result did not cover these failures.
